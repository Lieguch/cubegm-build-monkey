# 路线决策：如何停止"逐个差异 → 当根因 → 上机 → 再找一个"

> 触发：用户质问「你确认这次的方案不是在转圈？而是跳出来分析并结合互联网信息作根本性的解决方案方向？」
> 结论：**是转圈**。本文给出机制、类的边界、以及四条类级方案。
> 全部事实可复现；标注了每条是**已证**还是**待证**。

---

## 一、转圈的机制（精确表述）

我每一轮做的是：

```
从「重编后的机器码与原厂在**硬件可观测语义**上不同」这个**类**里
  → 采样一个成员（RELRO 页 ∩ .data / 立即数 44100 ≡ 符号 UpdateROM / MMIO 读被窄化成 ldrh）
  → 在静态层面与工厂逐条对比，确认它是"唯一差异"
  → 当作根因 → 修 → 交给你上机 → 再采样下一个
```

**这不是研究，是采样。** 而且"采样成本 = 一次真机往返"，所以看起来像原地转圈。

两个**结构性原因**（都可修）：

| # | 原因 | 现状证据 |
|---|---|---|
| 1 | **门禁是抽样式的，不是类级的** | `tools/mmio_width_audit.py` 的硬判据 W1 只覆盖 **2 个函数白名单**（`sfc_init` / `sunxi_gpio_init`）；其余 200+ 函数只有"提示"。类从未被证明覆盖完 |
| 2 | **沙箱不能复现真机的硬件约束** | SIGBUS 只在真机出现（沙箱里那块地址是普通 RAM）⇒ 每次判定必须真机往返一次 |

⇒ 只要这两条不变，**下一个成员必然还在类里**，我还会再找一个、再修一个。

## 二、类的边界（量化：它到底多大）

| 量 | 实测 | 复现 |
|---|---|---|
| 专有函数（须重建） | 213 个 `.c` | `find src/proprietary -name '*.c'` |
| **含外设基址常量的文件** | **3 个**（其中 1 个是**误报**：`0x2f2d2020` 是字符串 `" -/ "`） | 见下 |
| **真正做设备寄存器访问的文件** | **2 个** — `flash/…sfc_init.c`（SFC @`0x10208000`）、`flash/…sunxi_gpio_init.c`（CRU @`0x20000000`、GRF @`0x20008000`、GPIO0/1/2 @`0x2007c000/80000/84000`） | mmap 调用点 |
| 213 个文件里出现过 `volatile` 的 | **3 个 / 17 次** | 正则计数 |

**结论：类的边界很小且有限** —— 设备访问面只有 2 个文件、十几个函数。**它本来就不该分几轮去做。**

⚠ 同时发现**未修的同类实例**：`sunxi_gpio_init.c` 里那 **5 个 mmap 出来的设备基址（CRU/GRF/GPIO0-2）全部没有 `volatile`**（`g_sfc_reg` 已修）。
它今天恰好没有窄访问，所以现有 `mmio_width_audit` 的 W1 判 PASS —— **这正是"抽样式门禁"的漏洞**：判据没覆盖"顺序被重排"这一半。

## 三、本轮新增的硬事实（都是实证，不是推断）

### 3.1 ★ 工厂工具链指纹（`.comment` + `.note.gnu.gold-version`）

```
工厂 .comment  = "GCC: (GNU) 6.2.0"
                 "GCC: (Linaro GCC 4.9-2016.02) 4.9.4 20151028 (prerelease)"
工厂 note      = .note.gnu.gold-version → "GNU gold 1.12"
工厂符号足迹    = .constprop.(2) / .isra.(5) / .part.(5)   ← 全部是 GCC 特化
工厂**没有**    = .note.gnu.property（GCC≥11 才有）/ .note.gnu.build-id
```

**我们**：`zig 0.16.0` → **clang 21.1.0** + **lld** 链接。

⇒ 差异不是"版本新旧"，是**跨编译器家族 + 跨链接器**（GCC ↔ clang，gold ↔ lld）。

### 3.2 ★ 局部判决实验：窄化的边界条件（可复跑，已固化为门禁）

`tools/mmio_semantics_test.py`（4 条断言 + 3 态自证，实测 `exit=0`）：

| 变体 | 写法 | 产出（clang 21.1.0, `-Os`） | 判定 |
|---|---|---|---|
| **A** | 非 volatile 指针 + 只用低半字（= 修复前的真实形状） | **`ldrh r1,[r0,#44]`**，且在 `str` **之前** | ✗ 宽度错 + 顺序错 |
| **B** | **整块**寄存器指针声明 `volatile` | `str r1,[r0]` → `ldr r0,[r0,#44]` → `ands #65532` | ✓ 宽度+顺序都对 |
| **C ★** | **只对单次访问强转** `*(volatile u32*)&regs[0xb]` | `ldr` 对了，**但仍排在 `str` 之前** | ★ **反例** |
| **D** | 内联汇编访问原语 | `ldr`/`str` 各自落在 `@APP/@NO_APP` 内 | ✓ 编译器**零自由度** |

三条可执行纪律由此而来：

1. **窄化真实存在**（A 复现了真机 SIGBUS 的那条指令）—— 且**只在"低半字是死值"时发生**（我第一版实验让上半字也参与运算 ⇒ 复现不出，是我的实验构造错了，已更正）。
2. **必须"整块指针 `volatile`"，不能"单次强转"** —— C 变体证明单次强转只锁**宽度**、锁不住**顺序**。这条如果不知道，下一轮还会以"看起来修好了"的形态再炸一次。
3. **要彻底与编译器解耦，只能用访问原语**（D）。

### 3.3 关于"换 GCC 能不能整类解决"——诚实标注

工厂没窄化（事实）。原因**两种可能**，我**没有**区分它们：
- ① 原厂源码本来就有 `volatile`（Ghidra 反编译丢了限定符）；或
- ② GCC 6.2.0 在这个上下文不执行该窄化。

**两种可能都被 B/D 覆盖** —— 这正是选"恢复 volatile + 访问原语"作为主线的理由：它**对原因二选一不敏感**。换工具链是**优化项**，不是前提。

## 四、联网查到的权威做法（本轮"结合互联网信息"的部分）

| 结论 | 来源 | 对照我们的现状 |
|---|---|---|
| **`volatile` 不足以保证 MMIO 语义**：不解决"编译器进一步拆分访问 / 重排 / 合并 / 缺 fence"中的**任何一项** ⇒ 内核的答案是**一律走内联汇编访问器**（`readl`/`writel`） | LKML 讨论（Arnd Bergmann 原话），RISC-V sw-dev 列表 | 我们**没有**访问器层；`volatile` 是我们目前唯一的防线 |
| **clang 系编译器已知会对"位域/窄值"生成 `LDRH`，而 GCC/IAR 生成合适宽度**，在设备内存上触发异常 | TinyUSB/DWC2 在 Cortex-M7 上的实测分析（armclang 案例） | 与我们的观测**同族**（我们观测到 clang 21 窄化、工厂 GCC 6.2.0 未窄化） |
| **QEMU 可以精确复现"访问宽度非法 ⇒ 总线错误"**：memory region 的 `.valid.min_access_size` / `.valid.max_access_size` 定义可接受宽度，越界即"设备与总线相关行为（**machine check**）"；`.valid.accepts` 回调可直接**拒绝**事务 | QEMU 官方 memory API 文档 | ⇒ **沙箱能复现我们的 SIGBUS**，这是打破"每轮一次上机"的关键 |
| **Rockchip SFC 上游驱动一律用 32 位访问器**（`readl`/`writel`/`readl_poll_timeout`），寄存器偏移 `SFC_CTRL`/`SFC_CMD`/`SFC_ADDR`/`SFC_DATA`/`SFC_SR`/`SFC_FSR`/`SFC_VER`… | 上游 `drivers/spi/spi-rockchip-sfc.c` | 给我们一个**权威的寄存器模型**（比逐个猜偏移可靠） |
| **编译器指纹可查**：GCC 写 `.comment`（版本串）；链接器写 `.note.gnu.gold-version` | Unix.SE / CSDN 工具链逆向实践 | 已用于 3.1 |

## 五、根本性方案（四条，按"能否切断转圈"排序）

### ① 把"编译器自由度"从硬件访问层彻底拿掉（**类级、根治、今天可做**）
- 建 `src/compat/mmio.h`：内核式访问原语 `cgm_readl/cgm_writel/cgm_readw…`，全部内联汇编 + `"memory"` clobber。
- 规则（写进技能与门禁）：**任何从 `mmap` 设备基址派生的指针，其声明与所有派生游标一律 `volatile`；跨寄存器访问一律走原语。**
- 收益：MMIO 层**与编译器/优化档完全解耦** ⇒ 这一**类**消失，不会再"下一个"。

### ② 把门禁从"抽样"改成"类级"（**类级、今天可做**）
- 判据换成"**溯源式**"：找出所有 `mmap(…, 0x1xxxxxxx/0x2xxxxxxx)` 的返回值 → 追踪其所有派生指针 → 断言 ①源码带 `volatile` ②产物里不出现 <32 位访问 ③写读顺序与工厂一致。
- 覆盖**全部 213 文件**，不再用白名单。
- 现在就能修掉的同类实例：`sunxi_gpio_init.c` 的 5 个无 `volatile` 的 mmap 基址。

### ③ 让沙箱能复现真机约束（**切断"每轮一次上机"**）
- 在 CI 的 QEMU 里加一个 SFC/CRU 设备模型：`min_access_size = max_access_size = 4`，并用 `.valid.accepts` 拒绝更窄的访问 ⇒ 直接产生总线错误。
- 收益：**SIGBUS 本地可复现** ⇒ 判定不再消耗真机往返；也能对"修好了没有"给出**自动化**答案。

### ④ 工具链对齐实验（**单命令、今天可做，作为优化项**）
- 项目自带的 `tools/cnb_env.sh` **第 38 行本来就会装 `gcc-arm-linux-gnueabihf`** —— 这条工具链一直在手边，我只是从没用过（构建脚本默认值就是 `CC="${CC:-arm-linux-gnueabihf-gcc}"`）。
- 实验：用 GCC 重编 213 个专有函数，以「访存宽度直方图 + 指令序列相似度」对拍工厂，与 clang 的同一组数字**并排比**。
  - 若 GCC 显著更近 ⇒ 换工具链（并重跑全部门禁）
  - 若不显著 ⇒ **排除一个变量**，主线仍走 ①②
- 注意：GCC 对象 + zig 链接会撞 glibc 符号（`cnb_env.sh` 第 147 行已记录）⇒ 实验用 **compile-only 对拍**，不涉及链接。

## 六、诚实声明

- **转圈这件事我认。** 上一轮的 MMIO 修复本身是正确的（真机已从 `SIGBUS` 收敛到与原厂逐字相同的音频行为），但它的**方法**仍是"采样一个成员"，我不能说它不是转圈。
- 本文的 ①②③④ 中，**① ② 是类级的**（切断转圈）；**③ 是仪器级的**（把判定成本降到 0）；**④ 是优化级的**（可能再消掉一批残余差异，但不保证）。
- **仍未证**：①能否让设备进菜单（未上机）；④换 GCC 的收益（未做实验）。**不把它们说成已解决。**
- 我这一轮**又犯了一次同类错误**：第一版判决实验构造错了（让上半字参与运算 ⇒ 复现不出窄化），差点据此否定自己的上一轮结论。**教训：实验的"缺陷态"必须与真实代码形状逐字同构** —— 已写进门禁的自证里。
