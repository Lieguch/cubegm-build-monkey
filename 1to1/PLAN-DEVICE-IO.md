# PLAN-DEVICE-IO —— 设备侧证据采集的**结构性**修复方案

> 起因（用户原话）：**"实机测试并没有 150 秒，原因是 150 秒产生太多零散文件，SD 卡被写文件出错。"**
> 本文给出**根因**、**联网核实的依据**、**结构性方案**与**验收判据**。
> 所有结论都挂在 `L:\cubegm\_diag\*` 的实测痕迹上，不靠推测。

---

## 0. 先说结论（三件互不混淆的事）

| # | 结论 | 证据 |
|---|---|---|
| **A** | **MMIO 宽度/顺序修复在真机被证实**：同一条指令（`0x00501b84`），修复前 SIGBUS，修复后存活 | 见 §1 |
| **B** | **新故障点已定位到源码级**：`strtriml(r0=0x10a)` —— `strlen` 收到非法指针 | 见 §2 |
| **C** | **本轮证据之所以不完整，是采集端的结构性缺陷**（写入次数爆炸），不是被测程序的问题 | 见 §3 |

## 1. 结论 A：修复成立（A/B 对照，同一点、同一指令）

| 候选 | 二进制 | 尺寸 | 结果 |
|---|---|---|---|
| 1 阳性对照 | 原厂 `rkgame.bak` | 3,921,108 | 存活至超时 ✓ |
| 2 | `t4` 最小动态 ELF | 2,628 | `exit_code=0` ✓ |
| **3** | **`t1`【修复前】** | 5,663,896 | **SIGBUS(7)**，`si_addr=0xb6f1602c`、`r0=0xb6f16000`、**`PC=0x00501b84`** |
| **4** | **`t3`【修复后】** | 5,663,928 | **★ 存活至超时（程序在运行）** |
| 5 | `t2` diag【修复前】 | 5,709,244 | SIGSEGV，`LR=0x0000001c`（返回地址被破坏） |
| **6** | **`t6` diag【修复后】** | 5,709,564 | SIGSEGV，**`PC=strlen+0xc`、`LR=strtriml+0x24`**（可正常符号化） |
| 7 | `t5` B 线 v15 | 1,031,860 | 见 §1.2 |

**`0x00501b84` 离线读出的机器码 = `e1d012bc` = `ldrh r1,[r0,#0x2c]`** —— 正是那条 16 位窄化读；
修复版同点变成 `str r4,[r0]`（先写）+ `ldr r1,[r0,#0x2c]`（32 位读）。
**⇒ 同一地址、同一指令位置，修复前必崩 / 修复后存活 ⇒ 修复被真机证实。**

### 1.1 两侧 stdout 逐行一致（程序真的走到了同一位置）

`p3_0_out.txt`（原厂）与 `p3_3_out.txt`（t3）**逐行相同**（仅 `appname:` 一行按文件名不同）：


`t1`（修复前）**打印到完全相同的最后一行**，然后才在 `sfc_init+0x6c` 上 SIGBUS。
**⇒ 修复前的死点在 `snd_pcm_start failed: -32` 之后；修复后越过了它。**

### 1.2 `t5`（B 线 v15）—— 也是"能跑"的正面证据
`p3_6_out.txt`：
```
=== rkgame rebuild starting ===
=== rkgame rebuild starting ===
failed to apply hwparams: -22
```

### 1.3 ★ 判据缺陷（必须记下）
"存活至超时" = 8 秒内没被信号杀死。**它无法区分"正常运行"与"卡住"**。
`t3` 存活 ⇒ 只证明"不再 SIGBUS"，**不证明"跑到了原厂的位置"**。
⇒ 下一轮必须补**进度证据**（如原厂也会打印的下一行输出 / 打开的资源包），而不是只看"没死"。

## 2. 结论 B：新故障点 = `strtrim()` 链上的 r0 透传

设备现场（t6）：
```
crash addr (si_addr) = 0x0000010a
PC(r15) = 0x005fed30   →  符号 = strlen  + 0xc
LR(r14) = 0x005add78   →  符号 = strtriml + 0x24
r0      = 0x0000010a   ← 与 si_addr 相同 ⇒ strlen(0x10a)
r4      = 0x0000010a
```

源码对应（本仓）：
```c
/* src/compat/proto.h:141 */
extern gh_byte * strtriml();      /* K&R：strtrim 内以 0 参尾调用 */
/* src/proprietary/misc/FUN_0001f20c_strtrim.c */
char * strtrim(void) { strtriml(); return (char *)strtrimr(); }
/* src/proprietary/misc/FUN_0001f1a4_strtriml.c */
gh_byte * strtriml(gh_byte *param_1)
```

**机制**：`strtrim()` 调 `strtriml()` 时**不带实参**（这是**故意**保留原厂的 r0 透传语义）⇒
`param_1` = 调用链上游留在 `r0` 里的值 = **`0x10a`(266) = 一个整数** ⇒ `strlen(266)` ⇒ SIGSEGV。

**⇒ 这不是 `strtriml` 自身的 bug，而是「上游把整数当字符串传进了 `strtrim`」。**
下一步要做的：找出 `strtrim()` 的**唯一调用者**（`callers=1`），核对它传 r0 的来源；
对照工厂同路径（工厂在 `snd_pcm_start` 失败后会走哪条分支）。

★ 注意口径：**非 diag 版 `t3` 没崩在这里** —— 可能只是"8 秒内还没走到"，**不能解读为"没问题"**（见 §1.3）。

## 3. 结论 C：采集端的结构性缺陷（本轮的"SIGBUS"其实是我们自己的）

### 3.1 实测到的失败痕迹（都在文件里）
| 痕迹 | 说明 |
|---|---|
| `_diag/PROBE4.txt` 第一轮在**候选 5 中途**断掉（第 195 行），随后直接开始第二轮 | 写入中断 |
| `t6` 的**崩溃时映射被截在行中间**（`b6d31000-b6`） | **我在探针里已把 maps 上限设为"无上限"** ⇒ 不是缓冲截断，**是写盘失败** |
| **探针 v4 新增的"PC 处指令 + SP 栈"根本没打印出来** | 同上，写失败发生在它们之前 |
| `crash.txt` = **0 B**、`frames.bin` = **0 B** | 文件创建成功、内容写入失败 |
| `trace.log` = 28,788 B（上一轮 7,913 B） | `level=3` 生效后写入量 ×3.6 |

### 3.2 根因：**写入次数**爆炸，不是总字节数

单轮（7 个候选）产生的**文件操作**：

| 来源 | 每轮文件数 | 机制 |
|---|---|---|
| `LD_DEBUG=libs,init` + `LD_DEBUG_OUTPUT=/sdcard/cubegm/_diag/ldd_` | **7 个新建**（`ldd_.<pid>`） | **ld.so 每启动一个进程就新建一个文件**（§联网核实） |
| 探针候选输出 `p3_<idx>_out.txt` | 7 个（`O_TRUNC` 反复重写） | 每候选一次 |
| `PROBE4.txt` | 1 个持续 append | 每候选 dump **全量 maps（3–5 KB）+ 栈 512 B** |
| diag 垫片：`trace.log` / `frames.bin` / `frames.snap.bin` / `maps.start.txt` / `env.txt` / `crash.txt` | 6 个 | `frames.bin` 是**按帧写** ⇒ 8 秒内可能数百次 write |
| **设备侧 icube 会反复拉起 `rkgame`** | ×N 轮 | 每次重启**重建全部文件** |

**⇒ 量级：单轮 ~20 个文件、数百次 write；icube 多轮重启后 → 上千次小写 + 频繁 open/close。**

### 3.3 联网核实的依据（外部佐证）
- **SD/FAT 写入失败的已知机制**是「**频繁执行小数据量写入**、未释放文件句柄、长时间连续写超过卡内 GC 与缓冲能力」，
  与总容量无关；且**未 sync/close 就断电会导致 FAT 表损坏**。
  （来源：<https://blog.csdn.net/weixin_33226548/article/details/165497600>、<https://ask.csdn.net/questions/8174484/54979688>、<https://ask.csdn.net/questions/8463087>）
- **`LD_DEBUG_OUTPUT` 的行为**：ld.so 把每个被调试进程的日志**写成 `<OUTPUT><pid>` 一个新文件**
  ⇒ "每进程一文件"是它的固有语义，**不能合并**（只能不用它）。

### 3.4 ★★ 结构性方案（根治，不是加重试）

| # | 措施 | 把什么降下来 |
|---|---|---|
| **1** | **日志写 `tmpfs`，不写 SD**：探针与垫片的日志目录改为 `/tmp/cgm/`（RAM 盘）。**探针 v1 已实测 `/tmp/PROBE.txt rc=0` ⇒ 可写**。测试结束（或崩溃后）再**一次性合并**成 1 个文件拷回 SD | SD 上的写入次数 **数百 → 1** |
| **2** | **去掉 `LD_DEBUG` / `LD_DEBUG_OUTPUT`**。理由：`/proc/pid/maps` 已经给出完整加载映像，ld.so 步骤日志是**冗余的第二来源**，而它正是"每进程一文件"的元凶 | 每轮 **−7 个文件** |
| **3** | **候选输出合并为单文件**：不再 `p3_<N>_out.txt`，改为**一个** `out.txt`，用 `===CAND n===` 分隔；且用 `O_APPEND` 而非每轮 `O_TRUNC` | 每轮 **−6 个文件** |
| **4** | **`frames.bin` 改内存环形缓冲**，只在**崩溃/正常退出**时一次落盘；`level` 默认降到 **1**（生命周期+文件 open/close），需要时再用 `level=3` | 消除"按帧写"的数百次 write |
| **5** | **写入必须带返回值检查 + 显式失败标记**：任何一步 write/close 失败，立刻在**另一个路径**（`/tmp` 或 `/sdcard`）写一行 `### EVIDENCE-TRUNCATED reason=...`。**禁止"半截文件"冒充完整证据** —— 本轮就是被半截 maps 骗了一次 | 消除"静默丢失" |
| **6** | **缩短单轮**：候选超时 `8000ms → 3000ms`；候选数从 **7 → 2**（只跑 `t1`【修复前】与 `t3`【修复后】这组对照 + 原厂阳性对照 = 3 个）。其余候选按需另跑 | 单轮 **<20 秒** |
| **7** | **探针自身"文件数自检"**：启动时统计本轮**打算创建的文件数**并在日志首行打出来（`FILES-PLANNED=n`），实测结束时打 `FILES-CREATED=n`。两个数不一致 ⇒ 记录失败被量化 | 让"文件爆炸"变成可观测指标 |

### 3.5 平台侧的补充（不是替代）
上一轮已打通 **CNB 云开发 + qemu-arm-static**（8 核 16 G，`/sdcard/cubegm` 真机同款工作目录），
可把**逻辑/控制流**类验证全部移到云端，**不烧 CI 分钟、不碰 SD 卡**。
**但边界必须说清（已联网核实）**：**QEMU user mode 不使用 Soft-MMU ⇒ 无法判定 MMIO、无法建模外设**
（<https://www.profound-dt.co.jp/qemu-en/qemu_chap4_en/>）
⇒ 云端**原理上不可能**复现本轮的 `SIGBUS(7)`（那是 `/dev/mem` 上真实的总线错误）。
**⇒ 真机测试不可替代，但可以"只跑最后一跳"** —— 这也正是把单轮压到 20 秒以内、文件数压到个位数的意义。

## 4. 验收判据（下一轮，先写死）

| # | 判据 | 期望 |
|---|---|---|
| V1 | 阳性对照（原厂） | 存活至超时 |
| V2 | `t1`【修复前】 | 仍在 `0x00501b84` 崩 SIGBUS（**证明对照有效**） |
| V3 | `t3`【修复后】 | 不再 SIGBUS；**并且**要给出进度证据（见 V5） |
| V4 | **证据完整性** | `crash.txt` / 栈 dump / PC 指令**必须齐全**；出现 `EVIDENCE-TRUNCATED` 即判**采集失败**（不是被测程序失败） |
| V5 | **进度刻度** | 探针必须报告"`t3` 走到了哪一步"（新增判据，取代"没死=好"） |
| V6 | **文件数** | 单轮 `FILES-CREATED ≤ 4`；SD 卡上**只允许 1 个合并后的日志文件** |
