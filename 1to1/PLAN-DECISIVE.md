# PLAN-DECISIVE —— 跳出"改一个 bug → 上机 → 再抓一个"的循环

> 触发：用户质问「**看来你是依靠用户的测试来进行穷举试错？难道你没有跳出来在主要方向上有解决性的方案吗？**」
> 结论：**质问成立。** 当前节奏就是穷举循环，本文给出根因与方向性方案。

---

## 1. 诊断：循环的形状与**必然性**

```
修 1 个 bug ──► 请你插卡上机 ──► 抓到第 1 个崩溃 ──► 修 ──► 上机 ──► 抓到第 2 个 ──► …
```

**为什么这个循环"必然"低效**（不是我不够努力，而是结构决定的）：

1. **真机一次只暴露第一个错误。** 进程 SIGBUS 就死了，**它后面还有多少同类错误，这一轮完全看不到**。
   本轮实证：一轮设备测试（2 次探针运行、7 个候选）**只推进了一个故障点**
   —— `0x00501b84`（`ldrh`）→ `0x005fed30`（`strlen`）。其余候选的产出**对判据毫无增量**。
2. **每轮成本 = 你的人工（插卡/开机/等待/拔卡/回传）+ 采集端还可能失败**（本轮就因 SD 写失败丢了证据）。
3. **最要命的是第 1 条**：即使采集端完美，**"一次只看到一个错"这个性质不变** ⇒ 有多少个同类缺陷就要上机多少次。

★ **根因一句话**：**我把"判定能力"（谁来判断对不对）放在了真机上。**

## 2. 方向性方案：把判定能力搬回云端，真机降级为「最后一跳」

### 2.1 支柱 A —— MMIO 访存契约的**运行期**对拍（覆盖本轮 SIGBUS 那一整类）

**原理（关键，且绕开了 qemu 的固有限制）**：

> 我上一轮已联网核实：**QEMU user mode 不使用 Soft-MMU ⇒ 无法判定 MMIO、无法建模外设**
> （<https://www.profound-dt.co.jp/qemu-en/qemu_chap4_en/>）⇒ **不能指望 qemu 复现总线错误。**
>
> **但我们根本不需要 qemu 建模硬件**：用 `LD_PRELOAD` shim 把 `open("/dev/mem")` + `mmap`
> **偷换成普通匿名内存** ⇒ **每一次"寄存器访问"都变成 shim 里的一次函数调用** ⇒
> **宽度 / 顺序 / 偏移 / 方向 全部可见**。**⇒ 该方案不依赖 qemu 的硬件能力，所以成立。**

**能力已在仓库里**（不是我新造的）：
```c
/* tools/guest_shim/fake_mem.c:719 */
return sfc_fifo_next(size);   /* 数据寄存器：按本次访问宽度推进 FIFO */
/* fake_mem.c:722 —— 注释里已经在讨论 ldrh/ldrb 的差异 */
```
+ `tools/mmio_width_audit.py` 已有**静态**判据（比对反汇编里的 narrow 访存计数）。

**缺的一步（本次要做）**：把运行期的 `(seq, offset, width, dir)` 落成 trace，**两侧同环境各跑一次、逐项对拍**。

**⇒ 覆盖范围**：宽度窄化 / 顺序颠倒 / 偏移越界 —— **一轮跑完，一次列全**，不再"崩一个看一个"。

### 2.2 支柱 B —— 隐式寄存器约定的机械扫描（覆盖本轮 `strtriml` 那一整类）

**原理**：本轮的第二个崩溃是
```
PC = strlen + 0xc   ←  strtriml + 0x24 调用它
r0 = si_addr = 0x0000010a   ← 一个整数 266 被当字符串指针
```
对应源码：
```c
/* proto.h:141 */ extern gh_byte * strtriml();          /* K&R：空参数声明 */
/* strtrim.c  */ char * strtrim(void) { strtriml(); … } /* 0 实参调用 —— 靠 r0 透传 */
```
**这类"K&R 空参数 + 靠 r0 透传"的调用点，在 C 语言层面没有任何约束**（`f()` 表示"参数未知"，不检查实参）
⇒ **编译器可以合法地在 `strtriml()` 之前改写 r0** ⇒ 透传语义丢失 ⇒ 垃圾指针。
**这不是 `strtriml` 的 bug，而是一整类结构风险。**

**已有同类工具**：`tools/scan_varargs_fns.py`。
**缺的一步**：扫出全部「空参数声明 + 0 实参调用」的点，并对每个点**反汇编工厂的同一调用点**，
核对 `bl` 之前 r0 是否被改写（工厂没改写而我们改写了 ⇒ 违规）。

**⇒ 覆盖范围**：所有依赖隐式寄存器传递的调用点 —— **一轮列全**。

### 2.3 支柱 C —— 把"1:1"拆成可分别机械判定的不变量
仓库已有雏形：`prop_equiv.py` / `exec_set_diff`（我们的执行集合 ⊇ 工厂）/ `strict_ids.py` / `vermatch.py`。
**目标形态**：**一次云端运行输出「违规清单」**，而不是"第一个崩溃"。
每类不变量一个门禁：访存契约（A）、寄存器约定（B）、调用序、返回码、执行集合覆盖。

## 6. 诚实的边界

- **shim 只能覆盖它拦截到的映射**：需要知道设备寄存器区在哪（本例 SFC 区 0x400 @ `0x10208000`）。
  **未知设备区**覆盖不到 ⇒ 真机仍是最终仲裁。
- 因此本方案的目标不是"取消真机"，而是**把上机频率从"每个 bug 一次"降到"里程碑一次"**，
  并且让每次上机只承担**确认**，不承担**发现**。
- 若 X1/X2 失败 ⇒ 说明"运行期偷换"这条路在这个设备上不成立，我会立刻改为
  「静态 + 反汇编级调用约定扫描」为主、真机为辅，并明确告知。
