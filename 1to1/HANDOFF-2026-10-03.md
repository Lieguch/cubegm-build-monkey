## 5. ★ 新根因线索（机器码级，已定位到核心矛盾，尚未完全坐实 —— 交接给下一个模型继续）

### 5.1 死亡点定位

我方 `GetCoreIndex`（在云上产物 `build/ab/zig-Os.elf`，地址 `0x4fba1c`）反汇编：

```
4fba20: e59f5070  ldr r5, [pc, #112]   ; 载 GOT 偏移字面量
4fba30: e79f5005  ldr r5, [pc, r5]      ; r5 = *(GOT[0x4de28c])   ← 载 default_core_list 地址
4fba3c: e5d50000  ldrb r0, [r5]          ; r0 = *default_core_list 首字节  ← 死亡点
```

`diff_exec` 死亡现场 **O=R!@0x0 sz=1** 意味着 `r5 = 0`（GOT 条目在 Unicorn 沙箱里被读成 0）。

### 5.2 核心矛盾（这是新根因的方向）

| 事实 | 值 |
|---|---|
| 静态 `.got` dump 在 `0x4de28c` 处的值 | **0x003b0134**（= `DAT_003b0134`，一个 size=0 的占位符号） |
| 符号表 `default_core_list` | **0x003b0254**（6800 OBJECT GLOBAL section 4） |
| 工厂侧同函数 | 正确读到 `0x003b0254` 并做 strcmp×8 |

**矛盾**：我方 GOT 条目值 `0x003b0134` ≠ 符号地址 `0x003b0254`（差 0x120 = 288B）。
`default_core_list` 在 `src/data/factory_image.S` 里是 `.set default_core_list, __f_data_base + 0x1254`（绝对符号别名，非真实 `.word` 对象）。

### 5.3 下一步查证方向（按优先级）

1. **为什么 GOT 条目指向 0x003b0134 而非 0x003b0254**：疑似 lld 对 `.set` 绝对符号的 GOT 填充错误，
   或 `factory_image.S` 里 `default_core_list` 附近的 `DAT_003b01xx` 占位符顺序/对齐问题。
   对照：`src/data/factory_image.S` 中 `default_core_list` 前后几行，以及我方 `.got` 完整 dump 与工厂 `.got` 对比。
2. **为什么 diff_exec 沙箱里读到 0 而非静态值 0x003b0134**：可能是 GOT 区域未映射/未初始化；
   核对 `tools/diff_exec.py` 的 `_build_plt` / 数据区映射逻辑（GLOBAL 对象落在工厂地址 `('A', addr, w, rw)` 的归一规则）。
3. 这是"刻度 A（171 工厂数据符号依赖）"的一个**具体实例**：`default_core_list` 是工厂数据符号，
   我方引用它时 GOT 解析不正确。若坐实，可能需要把该符号搬进自有段（P1 架构收敛的正确子集）。

## 误判机制

§5.2 说的「GOT 条目 `0x4de28c` = `0x003b0134`」——
那个装 `0x3b0134` 的槽在 `.got+0x5b8 @0x4de210`，它属于 **`DAT_003b0134`**
（`FUN_002b6c14_FBA_Load.c:43` 在用），**与 `GetCoreIndex` 无关**。
**把两个不相关的 GOT 槽当成一对** ⇒ 假根因。

**纪律 142**：「GOT 里出现某个值」不是判据；判据 = **该槽属于哪个符号的引用点**。

## 已回退

## 簇 A 真正的差异（下一步查这个）
